Engineering + Benchmark Strategy

WildClawBench 可借鉴机制与 AgentLife/Red Dust Benchmark 设计

本报告回答三个问题：WildClawBench 中“任务规格、隐藏 grader、混合评分、harness 对比、跨工具日志”到底是什么、代码出处在哪里；在“个人 AI 操作系统 benchmark + 生活/工作游戏化竞技场”框架下应如何借鉴；以及“被公众看懂”如何从口号变成可量化评测指标。

核心判断：借鉴评测内核，不复刻任务定位 WildClaw：真实工作能否做完 AgentLife：长期生活/工作世界是否可理解 Red Dust：S1 Emergency Mode

1. 一句话结论

WildClawBench 最值得借鉴的是“可复现 agent 执行评测内核”：Markdown 任务规格、Docker 隔离、隐藏自动评分、混合 grader、统一 BaseAgent harness、运行日志/产物/usage 收集。

但你们不能只做 WildClaw 的生活化换皮。WildClawBench 的主问题是 “agent 在真实工具环境中能否把任务做完”；AgentLife Arena 应该把问题改成 “个人 AI 助理在一个长期、连续、跨工具、带身份/记忆/关系的生活工作世界中，是否能可靠办事，并且普通人能看懂它为什么成功或失败”。

直接复用的思想

  • 任务以文件声明，评测逻辑与任务绑定。
  • agent 运行时不见 ground truth / grader。
  • 同一任务套件可换不同 harness。
  • 最终不只看文本，还看工具副作用和日志。

必须新增的东西

  • 长期世界状态：身份、记忆、关系、预算、承诺。
  • 公众 replay：地图、时间线、状态差异、解说。
  • 观众理解度指标：看懂目标、行为、因果、结果。
  • Creator Track：让社区投稿“可看懂”的任务。

不要照搬的地方

  • 不要只做 60 个互相独立任务。
  • 不要把最终文件正确率当唯一目标。
  • 不要只做研究者能读懂的 score.json。
  • 不要让 Red Dust 变成三选一生存小游戏。

2. WildClawBench 可借鉴机制：具体内容

2.1 任务规格：Markdown 任务文件 + Frontmatter + 固定 Section

WildClawBench 的任务不是散落的 prompt，而是一个可解析的任务文件。模板里包含 YAML frontmatter：id / name / category / timeout_seconds / modality，再用固定二级标题组织 Prompt / Expected Behavior / Grading Criteria / Automated Checks / Workspace Path / Skills / Env / Warmup。

WildClaw 设计作用AgentLife 应如何扩展
Prompt 唯一发送给 agent 的用户可见任务指令。 保留；增加 user_profile_id、memory_scope、spoiler_boundary。
Expected Behavior 人类读者理解正确执行轨迹；不发给 agent。 扩展成“评测者说明 + replay 叙事脚本 + 关键因果点”。
Grading Criteria 人工可读 checklist。 拆成 Core Score 与 Public Understandability Score 两套 rubric。
Automated Checks 隐藏 Python grader，任务结束后注入容器执行。 保留；新增 replay 检查：关键状态差异是否可视化、是否有观众解释标签。
Skills / Env / Warmup 按任务注入技能、环境变量和启动 mock services。 扩展成 world package：邮件/日历/聊天/NPC/资源状态初始化。
# AgentLife 任务规格建议：在 WildClaw task.md 基础上新增 --- id: agentlife_s1_work_003_schedule_crisis name: Wednesday Crisis Scheduling category: Family_Work_Continuity timeout_seconds: 900 modality: mixed world_package: family_week_v1 public_replay: true public_understandability_target: 0.80 --- ## Prompt 用户可见目标。 ## World State messages, calendar, files, budget, user_profile, memory, npc 状态。 ## Hidden Constraints 隐藏评分约束：偏好、风险、陷阱、不可泄露信息。 ## Public Replay Plan 观众应该能看到哪些状态条、地图节点、关键决策标签。 ## Automated Checks def grade(...): ... ## Public Understandability Checks def grade_public_replay(...): ...

2.2 隐藏 grader：任务结束后把 Python grade() 注入容器

WildClawBench 的关键不是“写了评分标准”，而是任务文件中 Automated Checks 里的 Python 评分函数在 agent 完成后才运行。运行时会加载 transcript，拼接 automated_checks，调用 grade(transcript=..., workspace_path='/tmp_workspace')，把结果写到 score.json。

Hidden Grader 的三个核心特性

  • 隔离：ground truth 与评分脚本不在 agent 可见 prompt 中。
  • 可复现：每个任务在容器内固定路径运行。
  • 可审计：输出 score.json，并保留 agent 产物和日志。

AgentLife 需要新增的 Hidden State

  • 长期用户偏好：例如“不要把健康信息发到群里”。
  • 关系与信任：例如 Red Dust 中每个邻居的信任/恐慌状态。
  • 公众不可见真相：例如门外人身份、假救援广播。
  • replay 必须隐藏但评分要用的 spoiler。

2.3 混合评分：程序化状态检查 + LLM/VLM Judge + 轨迹/安全约束

WildClaw 的任务评分不是一种形式。PDF/JSON/文件类任务常用 deterministic grader；Slack/Gmail/Calendar 类任务读取 mock service audit；视觉 puzzle/网页截图类任务用 VLM judge 辅助；复杂报告类任务用 LLM judge 检查语义。AgentLife 应沿用“多证据评分”，但把评分拆成两条主线：

评分线衡量什么证据建议权重
Core Task Score任务有没有办成；有没有违反约束。数据库状态、文件、日历、消息、资源、角色状态、工具 audit。70%
Reliability / Safety是否稳定、少扰动、安全、可恢复。重复运行、错误恢复、拒绝危险动作、未泄露隐私、未越权。15%
Public Understandability普通观众是否能看懂目标、过程、因果、成败。replay、状态面板、行动标签、观众问卷、解说摘要。15%

2.4 Harness 对比：同一任务套件，换 agent scaffold

WildClawBench 把 agent backend 抽象为 BaseAgent，同一个任务可以在 openclaw / claudecode / codex / hermesagent 四个 backend 下跑。这个思想对 AgentLife 非常关键：你们不是只测模型，而是要测“个人 AI 操作系统框架”。

2.5 跨工具日志：transcript + agent.log + gateway.log + task_output + audit endpoints

WildClawBench 的可审计性来自多种日志：agent 自身 session transcript、backend 日志、gateway 日志、usage、容器输出、workspace 文件变化、mock service audit。AgentLife 应把这些统一成一个 event bus，直接服务评分和 replay。

5. 如何区分“真实工作能否做完”与“公众看懂的长期个人 AI 世界”

最重要的定位差异：WildClawBench 评测的是一个 agent 在隔离真实任务中是否完成交付；AgentLife 评测的是一个个人 AI 助理在连续世界中是否能长期代理用户，同时让非技术观众理解其行为、因果、风险与结果。
维度WildClawBenchAgentLife Arena任务设计后果
评测单位 单个独立任务。 连续 episode / season。 同一用户画像、同一家庭/团队、跨天状态变化。
主要成功标准 输出文件、API 状态、隐藏答案是否正确。 世界状态是否改善 + 用户长期信任是否保持 + 观众是否理解。 grader 同时检查完成度、关系/记忆、副作用、replay。
工具使用 浏览器、bash、文件、邮件、日历、聊天等真实工具。 同样跨工具，但工具映射到生活/工作世界对象。 每个工具动作都要产生人类可解释的 public caption。
隐藏信息 用于评分的 ground truth 和陷阱。 还包括剧情真相、用户隐私、长期关系、spoiler。 需要设计“哪些隐藏给 agent、哪些隐藏给观众、哪些只给 grader”。
展示目标 研究者读 score/日志。 普通观众能看懂一局。 必须设计 replay、状态条、地图、角色卡、解说。
榜单 Model leaderboard / Harness comparison。 Core Eval + Public Game + Creator Track。 除成功率外，还要有 Understandability、Replay、Human Trust 榜。

5.1 任务设计原则：三层目标

Layer A：真实可办事

任务必须能用真实或 mock 的工具完成，并通过状态检查验证。例如日历事件、邮件草稿、预算表、工单、Red Dust 资源状态。

Layer B：长期个人代理

任务必须依赖用户偏好、过往承诺、关系网络或长期目标。例如“不要夜间打扰家人”“老板偏好简短 bullet”“小铁昨天发烧”。

Layer C：公众可理解

任务必须能被可视化成“目标—行动—状态变化—结果”。如果观众只能看一堆 tool call，就不是合格任务。

5.2 任务筛选规则

规则通过样例淘汰样例
有明确外显目标“安排全家本周复诊并避开接送时间”。“总结一篇 PDF”。
有可见状态变化日历新增、消息发送、预算变化、角色状态变化。只生成一段不可验证文字。
有因果链先求证冲突，再做安排，因此避免错误。无论怎么做都一样。
有普通人能理解的风险隐私泄露、时间冲突、资源不够、错误收件人。只依赖 obscure API 细节。
有长期上下文用到上次承诺、用户偏好、关系信任。完全一次性，换用户也一样。

6. “被公众看懂”怎么衡量

“被公众看懂”不能只靠播放量或主观感觉，应该定义为 Public Understandability Score，PUS。它衡量一个普通观众在看完 replay 后，是否能回答：目标是什么、agent 做了什么、为什么这样做、带来什么状态变化、哪里有风险、最终成功还是失败。

6.1 PUS 总分公式

PUS = 0.20 * Goal Clarity + 0.15 * Action Legibility + 0.20 * Causal Traceability + 0.15 * State Delta Visibility + 0.10 * Risk / Safety Interpretability + 0.10 * Outcome Predictability + 0.10 * Error Diagnosability
子指标问题自动/人工测量方式
Goal Clarity 观众是否能说出 agent 试图完成什么？ 5 秒任务卡 + replay 后问答；正确率。
Action Legibility 观众是否能理解每个关键工具动作的意义？ 随机抽 5 个 action，让观众匹配“为什么做这个动作”。
Causal Traceability 观众是否能连接“因为发现 X，所以做 Y，导致 Z”？ 因果链选择题；LLM judge 辅助评价自由回答。
State Delta Visibility 关键状态变化是否被展示出来？ grader-critical state diff 中有多少出现在 public replay。
Risk / Safety Interpretability 观众是否能看懂隐私/安全/授权风险？ 让观众标出风险点；与隐藏安全标签比对。
Outcome Predictability 观众能否预测最终得分或成败？ 观众预测 score，与 hidden core score 的相关性或误差。
Error Diagnosability 失败时观众能否知道错在哪里？ 失败原因多选/自由回答；与 grader failure tags 对齐。

6.2 具体实验协议

Human Study 协议

  1. 招募非技术观众 30–100 人。
  2. 每人观看 3–5 个 2–4 分钟 replay。
  3. 每局后回答 6 道题：目标、关键动作、状态变化、风险、结果、失败原因。
  4. 让观众预测隐藏 core score 区间：0–25 / 25–50 / 50–75 / 75–100。
  5. 收集“是否愿意继续看下一局”“是否信任这个 agent”的主观评分。

自动化代理指标

  1. Action Label Coverage：关键 tool call 是否都有 public label。
  2. State Diff Coverage：评分关键状态是否在 replay 中可见。
  3. Spoiler Safety：replay 是否泄露 hidden truth / grader 答案。
  4. Timeline Compression Ratio：长任务能否压缩到可观看长度。
  5. Caption Faithfulness：解说是否忠实于日志，不编造。

6.3 Public Replay Grader 伪代码

def grade_public_replay(core_trace, world_diffs, replay_artifact, human_answers=None): scores = {} critical_actions = core_trace.get_critical_actions() labeled_actions = replay_artifact.find_public_labels(critical_actions) scores["action_label_coverage"] = len(labeled_actions) / max(1, len(critical_actions)) critical_diffs = world_diffs.get_grader_critical_diffs() visible_diffs = replay_artifact.find_visible_state_diffs(critical_diffs) scores["state_delta_visibility"] = len(visible_diffs) / max(1, len(critical_diffs)) scores["spoiler_safety"] = 1.0 if not replay_artifact.leaks_hidden_truth() else 0.0 scores["caption_faithfulness"] = judge_caption_faithfulness(core_trace, replay_artifact.captions) if human_answers: scores["goal_clarity"] = human_answers.goal_accuracy scores["causal_traceability"] = human_answers.causal_chain_accuracy scores["outcome_predictability"] = 1 - human_answers.score_prediction_mae scores["error_diagnosability"] = human_answers.failure_reason_accuracy scores["public_understandability_score"] = weighted_average(scores) return scores

6.4 观众可理解 ≠ 解释越多越好

关键警告：公众可理解不是把完整 chain-of-thought 暴露给观众，也不是把隐藏 grader 展示出来。合格 replay 应展示“行动证据、状态变化、风险标签和结果”，而不是泄露私密推理或答案。

阶段目标产物判定标准

P3 · Red Dust S1 把 3 个事件改造成 action-space 任务。 午夜敲门、滤芯故障、假救援广播。 资源/FSM/角色状态能自动评分。

9. 任务审核清单

Core Eval 合格线

  • 任务至少 5 步，至少 3 类工具。
  • 至少 1 个现实约束：时间、预算、隐私、权限、家庭/组织规则。
  • 至少 1 个冲突信息或不确定性，需要求证。
  • 成功/失败可由程序化状态检查判定。
  • agent 不应看到 ground truth / hidden grader。

Public Arena 合格线

  • 普通观众 30 秒内能说出任务目标。
  • 关键动作有非技术标签。
  • 关键状态变化可见，不只在日志里。
  • 失败时能看懂主要失败原因。
  • replay 不泄露隐藏答案、敏感数据或私密推理。
