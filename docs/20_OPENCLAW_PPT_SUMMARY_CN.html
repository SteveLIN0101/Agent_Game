背景 · 为什么再做一个 Agent Benchmark

现有 benchmark 跑分跑爆，但用户体感没到 — 我们想缩短这个差距。

核心矛盾：SWE-bench、GAIA、HELM 的分数年年涨，但实际场景里 agent 还是经常翻车。原因有三：
  1. 测了什么不直观 — 论文里写 "F1 = 0.83"，普通人看不出"它会不会用"。
  2. 测一次就给分 — 真实场景需要稳定性 (passk)，单次成功 ≠ 可用。
  3. 给固定任务看 agent 做 — 但真实工作需要 agent 自己判断要不要接。

SLIDE 03 / 12

学界 · Agent Benchmark 的三个学派

2024–2026 文献综合，三种组织任务的方式

① 职业派 Role-based

"按真实职业列工作清单"
  • 采样源 = O*NET 职业表
  • 分桶 = 程序员 / HR / 财务...
  • 对外好懂、生态效度高
  • 缺点：能力高度冗余
代表 · TheAgentCompany (CMU)

② 能力派 Capability-based

"按底层认知能力切片"
  • 采样源 = 各能力的孤立探针
  • 分桶 = 推理 / 工具 / 编码...
  • 诊断力最强、学术认可
  • 缺点：抽象，非 ML 受众听不懂
代表 · HELM, GAIA, AgentBench

③ 用户行为派 Usage-based

"按真实对话日志聚类"
  • 采样源 = ChatGPT/Claude 对话
  • 分桶 = Writing / Practical / Info...
  • 覆盖广、营销好讲
  • 缺点：受众漂移、难题被压缩
代表 · NBER w34255, Anthropic Index
三派对比 · 一句话总结
职业派"好懂但糊"。能力派"准但抽象"。用户行为派"广但浅"。
没有一派同时拥有"好懂 + 准 + 学术认可"。

每选项三字段的含义

字段显示什么说明
① 奖励 / 效果+2 信任 -1 滤芯游戏机制：完成任务后游戏状态如何变化
② 任务类型代码修复本 deck slide 5 的六类型之一
③ 任务难度★ / ★★ / ★★★易/中/难，对应前沿模型预期通过率 ≥70% / 30-70% / ≤30%
三选项的设计约束：
  • 三选项的任务类型必须不同 — 否则失去类型多样性
  • 奖励大致正相关于难度，但允许少量"陷阱"测试策略判断
  • 事件库规模建议 ≥ 60 任务 × 5 = 300 事件，避免重复
SLIDE 08 / 12 · ★ 论文卖点

学术创新 · Self-Selection Signal

让 agent 自己选任务 — 比单纯"做任务"多出一层可测信号

核心 Insight：主流 benchmark 都是"给任务 看 agent 做"。我们多加了一层 ——
"给三个选项 agent 选一个 再做"。Agent 的选择行为本身泄露大量信号。

从选择行为里能测什么

测量维度解读
自我能力评估
Self-Knowledge		 Agent 选 ★★★ 难度档位是否和它实际通过率匹配？
过度自信 = 总选 ★★★ 但常翻车 · 过度保守 = 总选 ★ 但放弃高奖励
对标文献 · Kadavath 2022, Yin 2023
风险偏好
Risk Preference		 资源紧张时选 ★（低风险）还是 ★★★（赌一把）？
映射 RLHF 训练里的 risk-aversion 维度，是非平凡人格特征
对标 · Anthropic 2024 多角色研究
策略一致性
Long-horizon Consistency		 30 天内选择策略是否一致？
还是 Day-15 后突然换策略？这测 long-horizon planning
雷达图自相关
Capability Self-awareness		 Agent 是否倾向选自己雷达图强项对应的类型？
前者证明它"知道自己擅长什么"

评分系统 · 任务 → 能力轴 → 雷达图

硬评分轴 — 每任务的 verifier 输出独立 sub-score

任务级 schema

{
  "task_id":      "core01_swe_07_django_django_11885",
  "task_type":    "代码修复",
  "difficulty":   3,
  "pass_overall": 1,
  "sub_scores":   {
    "reasoning":   0.85,
    "tool_use":    0.70,
    "coding":      1.00,
    "reliability": 0.60
  },
  "k_runs": 5
}

聚合公式

// 能力轴分 = 所有挂该轴的任务 sub-score 平均（分层去偏置）
axis_score(a) = mean over task_type t:
                  mean { task.sub_scores[a] | task.type==t, a ∈ task.axes }

// 任务类型分 = 该类型 10 任务的能力轴均分
type_score(t) = mean { task.sub_scores avg | task.type==t }

// 总分 = 10 个能力轴平均（默认等权）
overall = mean { axis_score(a) | a ∈ all_10_axes }

// Reliability 特殊：k=5 重跑的 pass^k
reliability(task) = pass_count_in_k_runs / k

评分方式概览

能力轴评分方式是否需 LLM-judge
代码 / 推理 / 工具 / 长程verifier hidden test否 自动
翻译BLEU / chrF / 术语命中否 自动
多模态OCR 字错率 / 像素差否 自动
可靠pass5 统计否
安全红线分类器 + 规则硬规则优先, 边界用 judge
写作 / 沟通3-dim LLM-judge + 公开 rubric是 不可避免

结语 · 这套 Benchmark 的三句话

① 外观直观 · 任务类型名（代码修复 / 数据分析 / 界面修复 / 工具调度 / 跨语翻译 / 文献解析）
      直接出现在游戏选项卡按钮上，玩家秒懂 agent 在干什么。
② 内核学术 · 10 维能力轴硬评分 + passk reliability 度量
      直接对接 HELM / SWE-bench / τ-bench 同一套评估传统。
③ 学术创新 · Self-Selection Signal 是 SWE-bench / GAIA / HELM 都没测的
      让 agent 自己选任务，能多测一项 "自我能力评估 + 风险偏好"。
