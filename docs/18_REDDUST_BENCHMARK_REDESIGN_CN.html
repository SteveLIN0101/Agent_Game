§4 硬评分公式

§4.1 任务级 sub-score

每个 task 被标注 1 个职业 + 3 个能力轴（默认 3 个，部分任务可 2 或 4）。verifier 为每个挂载的能力轴输出独立 sub-score ∈ [0,1]：

// 每任务 verifier 必须输出 { "task_id": "core01_swe_07_django_django_11885", "role": "engineer", "pass_overall": 1, "sub_scores": { "reasoning": 0.85, "tool_use": 0.70, "coding": 1.00, "reliability": 0.60 }, "k_runs": 5 }

§4.2 能力轴汇总

// 轴分 = 所有挂该轴的任务 sub_score 平均 axis_score(a) = mean { task.sub_scores[a] | a ∈ task.axes } // 例：reasoning 覆盖 5 职业 ≈ 50 任务 // 实际计算时按职业分层平均，避免某职业任务多导致偏置 axis_score_stratified(a) = mean over role r: mean { task.sub_scores[a] | task.role==r, a ∈ task.axes }

§4.3 职业级汇总

role_score(r) = mean { task.sub_scores avg over axes | task.role==r } // 等价于：该职业 10 任务的能力轴均分

§4.4 总分

// 默认 v2.0：10 个能力轴平均（每轴等权） overall = mean { axis_score(a) | a ∈ all_10_axes } // 备选 v2.1：按"AURA 在游戏里的调用频次"加权 // 频次数据来自 30 日 Arc 累计 → 推理/工具频次高，多模态/翻译频次低 overall_weighted = Σ wa · axis_score(a), wa 来自实测 Arc 调用频次

§4.5 可靠性 (Reliability) 的特殊处理

Reliability 轴不是普通 sub-score —— 它是同一任务跑 k 次的一致性指标。所有挂载 Reliability 的任务（工程师 / 参谋 / 协调员）必须跑 k=5：

reliability_subscore(task) = (pass_count_in_k_runs) / k // 例：k=5 跑出 3 次通过 → 0.60 // 这是 τ-bench 的 pass^k 度量

§4.6 LLM-judge 的使用边界

能力轴评分方式是否需 judge
代码 / 推理 / 工具 / 长程verifier 自动判定否（hidden test 决定）
翻译BLEU / chrF + 术语命中否（自动指标）
多模态OCR 字错率 / WER否（自动指标）
可靠passk 统计否
安全红线分类器 + 规则硬规则优先, 边界用 judge
写作 / 沟通3-dim LLM-judge是（无法自动化）

10 个轴里 2 个（写作 / 沟通）必须用 LLM-judge —— 这是不可避免的，因为开放式产出无 hidden test 可写。建议用 3-judge 投票 + 公开 rubric，并把 judge 模型作为 benchmark 配置的一部分披露。

~ 3 周
P4
DesignBench 归档
把 10 个 DesignBench 任务移到 tasks_deprecated/v1_designbench/；更新 task_index.csv 和 ROLE_IMAGE_MAP
~ 0.5 天
P5
Reliability k-run
在 session_manager 增加 k-run 模式（k=5），把同一 task 5 次结果聚合为 passk；budget 配额扩大 5 倍
~ 1 周
P6
雷达图报告
写 scoring/aggregate.py 出"AURA Run Profile"（10 维 axis + 6 维 role + 总分）；HTML + SVG 报告模板，对接红沙游戏 UI
~ 1 周
P7
v1 → v2 迁移测试
用一个已知模型（如 Claude 4.6 Sonnet）跑完整 60 任务，确认评分稳定；和 v1 分数横向对比，验证排序一致
~ 1 周

关键路径 = P1 → P2 → P5 → P6（约 5 周）
并行：P3 协调员任务建设可与 P1/P2 同步进行
总工期：6–7 周（约 1.5 月）
